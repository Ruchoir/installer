## Common rules (every Ruchoir repository)

These rules are the same in every repository of the Ruchoir organization. The rest of this file adds
what is specific to this repository, and never contradicts this block.

### Golden rules

1. **No AI references anywhere.** Not in code, comments, commit messages, branch names, pull
   requests, docs or metadata. No `Co-Authored-By` naming a tool, no "generated by" note, no agent
   signature. `AGENTS.md` is the only AI-facing file allowed in a repository. Write and commit exactly
   as a human contributor would.
2. **European or neutral dependencies only.** No US or non-EU hosted service at runtime: no cloud
   provider, CDN, font service, analytics or outbound telemetry. For libraries, prefer a European or
   neutral community alternative when one is functionally equivalent. Check and record the origin and
   governance of anything new before adding it; when in doubt, ask. The accepted exceptions are listed
   in `Ruchoir/.github`, `dependency-exceptions.md`, and nowhere else: a repository never adds one on
   its own.
3. **English only** in the repository: code, identifiers, comments, docs, commits, branches, issues,
   pull requests. What the interface says to people lives in its dictionaries (see "Interface text").
4. **Document thoroughly.** Module docs, doc comments on public items, and a note wherever the
   reasoning is not obvious from the code. A structural decision gets an ADR.
5. **Keep the docs current, unprompted.** When a change alters a decision, the stack, the scope or a
   convention, update `README.md`, `AGENTS.md` and the relevant docs in the same change, so they never
   drift. Record a gotcha the first time it costs an hour, not the second.
6. **No em dashes (U+2014) anywhere**: code, comments, docs, commits. Use a colon, a comma,
   parentheses or a plain hyphen.
7. **Product boundaries.** A repository never imports another product's internal code. It reaches
   another product only through that product's public API or published events, and shares code only
   through a versioned package of `Ruchoir/core`.
8. **Every repository stands alone.** It builds, tests and starts without the source of any other
   repository checked out. Other services are replaced by test doubles built from their published
   contracts.

### Git and pull requests

- `main` is protected. Every change goes through a pull request, and the required checks must pass.
  A review is welcome but not required while the team is two developers.
- Branches: `feat/`, `fix/`, `refactor/`, `perf/`, `docs/`, `test/`, `build/`, `ci/`, `chore/`,
  then a short English name in kebab case.
- Commits and pull request titles follow Conventional Commits in English
  (`build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test`, optional scope, `!` for a break).
  Pull requests are squash-merged, so the title becomes the commit. The one exception is code moved
  with its history from another repository: that pull request is merged with a merge commit, and the
  `conventions` check skips the merge commit's own subject (ADR 0009).
- No ticket identifiers, lot names or code names in branches, commits or pull requests: say what the
  change does.
- Never commit a secret. `.env` stays out of git; `.env.example` documents every variable.
- A contributor from outside the team signs the contributor licence agreement (`CLA.md` of
  `Ruchoir/.github`) on their first pull request; a check asks for it.

### Releases

- Each service (`propolis`, `hub`, `drive`, `calendar`, `chat`) is versioned with SemVer,
  independently of the major version of its API.
- A service's tag `vX.Y.Z` builds and publishes a signed image to `registry.ruchoir.com`, with
  release notes drawn from the commits. **A tag deploys nothing.** Every instance, the testers'
  included, is updated through the installer, like a customer's.
- These two rules are for the services. Any other repository (an app, the installer, a site) says in
  its `AGENTS.md` what its tag publishes.
- `Ruchoir/core` is released as one version: every crate and package carries it, and a product pins
  one version of `core` for all of them (ADR 0013).

### Decisions

- Each repository keeps its ADRs in `docs/adr/NNNN-short-title.md`, numbered from `0001` within it.
- A decision that touches more than one repository is recorded in `Ruchoir/.github` (`docs/adr/`), and
  each repository it affects links to it from its `AGENTS.md`.
- An accepted ADR is never rewritten: a later ADR supersedes it, and both say so.

### Licences

- Services, apps and the installer (`propolis`, `hub`, `drive`, `calendar`, `chat`, `desktop`,
  `mobile`, `installer`): `AGPL-3.0-only`.
- `Ruchoir/core`, which holds what another developer embeds in their own code (the Propolis SDK, the
  API clients, the design system): `MPL-2.0` (ADR 0014). `Ruchoir/.github`: `MIT OR Apache-2.0`.
- Each package declares its licence in its manifest. A repository holding code under two licences
  ships both texts. Fonts keep their own licence (IBM Plex, OpenDyslexic: OFL).
- The enterprise module is proprietary. It is never published, copied or vendored into a public
  repository, and a public repository never names, fetches or requires it.

### Dependencies

- Pin exact versions. Bump deliberately, to the latest stable release verified against the live
  registry, never from memory.
- Record the origin and governance of each dependency next to it in the manifest, as a comment.
- The reusable CI checks dependencies against `dependency-exceptions.md` (cargo-deny for Rust) and
  audits them for known vulnerabilities on every push.

### Security and privacy

- Strong encryption in transit and at rest. TLS everywhere, `wss://` only.
- The server never trusts the client: every request is authenticated and authorized server-side.
- Never log a password, token, secret or private content.
- A vulnerability is reported privately, through GitHub's private vulnerability reporting, never in
  an issue (`SECURITY.md` of `Ruchoir/.github`).
- Minimise data. Every service exports and deletes a person's data when Propolis announces a deletion,
  and a test proves it.

### Interface text

- The interface speaks French, English, Spanish, German, Italian and Polish. French is the source:
  what the product is written in, what a missing key falls back to, what the others translate.
- Each repository with an interface keeps its six dictionaries and runs the `i18n:check` provided by
  `Ruchoir/core`. Strings shared by several products (common buttons, common errors, product names)
  come from the shared package of `core`.
- One sentence, one key. French typography: a non-breaking space inside « » and before `?`, `:`, `;`
  and `!`.

## This repository

The installer sets up a self-hosted Ruchoir instance à la carte. Propolis, the hub and the reverse
proxy are always installed, plus the products chosen (choosing the chat also installs the drive). It
keeps the manifest of installed products, which the hub publishes at a `.well-known` address.

**Status:** v0. `ruchoir-install` writes an instance's directory and runs it with Docker Compose:
Propolis, the hub and the proxy, in production (`init`, `up`, `down`) or on `*.localhost` (`dev`).
The products are chosen with `--products`: the drive, with Garage for its files and
Euro-Office, its office engine, which always comes with it, the calendar, on its own or beside the drive, and the chat, which always brings the drive
(`REQUIRES` in `src/lib.rs`, applied where the products asked are checked).

Lab, the team's internal tool, runs beside them on a development instance only (`dev --lab`,
`Instance::with_lab`): its service, database and secret, its route at `lab.<domain>`, and the
confidential client `ruchoir-lab` in Propolis's registry (`propolis:organizations.read` to read the
organisation it lets in). It is in `Instance::services()` but never in the manifest
(`Instance::listed()`), so it is kept across runs by its client key (`lab_kept`), not by the
manifest. `LAB_ORGANISATION` is left to the operator (`${LAB_ORGANISATION:-}`). Its runner
(`lab-runner`, image `ruchoir/lab-runner:dev` built from `lab/runner`) shares the proxy's network
namespace (Chromium sends `*.localhost` to the loopback) and trusts the development authority
(`NODE_EXTRA_CA_CERTS`, which the image also adds to Chromium's store); the screenshots go to the
`lab-captures` volume, which Lab reads.

### How it is built

- `src/lib.rs`: the instance (domain, mode, products) and `init`, which writes the directory. The
  products installed are those of the manifest written last: `--products` adds to them, never
  removes, and an `init` without it keeps them.
- `src/secrets.rs`: what is generated once and kept (`.env`, each client service's Ed25519 keys, the hub's VAPID key).
  A product's secrets and keys are made when it is installed: for the drive, `keys/drive-auth.pem`
  and `keys/drive-events.pem`, its database password, Garage's RPC secret and admin token, and its
  S3 key (`DRIVE_S3_ACCESS_KEY_ID`, `GK` and 24 hexadecimal characters as Garage makes them).
  For the calendar, `keys/calendar-auth.pem` and `keys/calendar-events.pem`, its database password
  and `CALENDAR_SECRET_KEY` (64 hexadecimal characters, which encrypts the tokens of people invited
  by address: replacing it voids the links already mailed).
  For the chat, `keys/chat-auth.pem`, `keys/chat-events.pem` and its database password: it keeps no
  encryption key of its own and sends no mail.
  Running `init` again never replaces a secret or a key: the services and their data depend on them.
- `src/render.rs`: every other file, written anew each time from the instance and its secrets:
  `manifest.json`, `compose.yaml`, `traefik/`, `propolis/clients.toml`, `hub/subscriptions.toml`,
  `postgres/init.sh`, and with the drive `garage/garage.toml` and `office/`.
- Discovery: apps and pages start at `https://hub.<domain>/.well-known/ruchoir-manifest`. The hub
  serves `manifest.json` (`version`, `domain`, and `services`, each installed service with its `url`),
  mounted read-only at `/manifest/manifest.json` with `HUB_MANIFEST` pointing at it. Each service then
  answers `/.well-known/ruchoir-product`. The file is mounted, not copied, so a later `init` that adds
  a product is served without restarting the hub.
- What a product is given by the others is written where both are known: with the drive and the
  calendar, the calendar's client asks `drive:held.manage` (the drive declares it), the calendar
  gets `CALENDAR_DRIVE_URL` and hears `drive.file.*` at the hub, and the drive gets the calendar's
  origin in `DRIVE_PRODUCT_ORIGINS` (`render::drive_product_origins`, every product but the drive).
  `HUB_PAGE_ORIGINS` lists every product's origin (`render::page_origins`).
  The chat always has the drive: its client asks `drive:held.manage`, it gets `CHAT_DRIVE_URL`,
  hears `propolis.*` and `drive.file.*`, and its origin is in `DRIVE_PRODUCT_ORIGINS`. Its client
  declares `chat:cards.post` and `chat:channels.read` (`render::CHAT_SCOPES`); with the calendar,
  the calendar's client asks both and the calendar gets `CALENDAR_CHAT_URL`.
- `src/garage.rs`: Garage, the drive's object store: its configuration, and the commands that
  prepare a fresh one (pure functions, unit-tested).
- `src/office.rs`: Euro-Office, the drive's office engine: its service, the drive's settings for it
  (`DRIVE_OFFICE_URL`, `DRIVE_OFFICE_PUBLIC_URL`, `DRIVE_WOPI_*`), and the files it mounts.
- `assets/office/`: those files, built into the binary (`include_bytes!`) and written to the
  instance's `office/`: the engine's settings `local-production-linux.json` (a save every ten
  minutes), the Ruchoir themes the drive's sessions ask for, and the patched `editor-wopi.ejs` and
  `visioeditor-index.html`. Copied unchanged from the monolith's `infra/office/` (`Ruchoir/ruchoir`
  at `e3e76d8`), whose `README.md` explains each patch; the themes there are generated by the
  monolith's `tools/office-themes`. The patched pages are Euro-Office's, under its licence
  (AGPL-3.0). None of the files names anything of an instance, so they are written as they are.
- `src/dev_ca.rs`: in development, a local certificate authority the proxy and the services trust.
  Its certificate is issued again, by the same authority, when a product adds a host.
- `src/hosts.rs`: the hosts-file block of a development instance (`ruchoir-install hosts`), for
  the programs that do not resolve `*.localhost` (anything but a browser on Windows): one line per
  host on each loopback, between marker lines, so `--write` replaces its own block and nothing else.
- `src/migrate/`: `migrate`, which moves an instance of the monolith into this one (ADR 0001,
  runbook `docs/migrate-monolith.md`). `instance.rs` does the Docker part (services stopped,
  `compose.migrate.yaml` publishing PostgreSQL and Garage on the loopback, the dump restored into
  `monolith_source`); `db.rs` moves rows as JSON (`json_populate_recordset` casts them); one module
  per service says, in a table, where each monolith table goes and what is left behind;
  `replica.rs` writes each product's copy of the organisations and its part of each role's
  permissions.
- `src/main.rs`: the command line.

### Gotchas

- `migrate` writes the services' tables directly: `tests/fixtures/<service>-schema.sql` are their
  schemas (`pg_dump --schema-only` after their migrations, `\restrict` lines removed), and
  `monolith-schema.sql` the monolith's at its last commit. When a service's migration changes a
  table `migrate` writes, take its fixture again and run `tests/migrate.rs` (it needs
  `RUCHOIR_MIGRATE_TEST_DATABASE`, see the README).
- A JSON row given to `db::insert` names its columns; a column only some rows name is null in the
  others, not its default.
- Propolis makes the three system roles of an organisation when it is inserted (a trigger), with
  new ids: `identity.rs` gives them the monolith's ids right after.

- The services run as the owner of the instance's directory (`RUCHOIR_USER` in `.env`, set on
  Linux): its private files are `0600`, and the images' own user could not read them.
- The containers reach each other at their public names (`id.<domain>`) through aliases of the proxy
  on the instance's network, so issuer URLs match inside and out. In development they trust the
  local authority through `SSL_CERT_FILE`.
- The registry written for Propolis must pass Propolis's own check (`deny_unknown_fields`,
  `https` addresses, a `client_auth` key for `private_key_jwt`): change both together.
- Every registry also lists Ruchoir's apps, `ruchoir-desktop` (`http://127.0.0.1/callback`, any port)
  and `ruchoir-mobile` (`com.ruchoir.app:/oauth/callback`): public (`none`, PKCE), keyless, no
  resource of their own; Propolis gives its first-party apps a token for the hub and every product.
- Operators put their own changes in `compose.override.yaml`, which `init` never touches.
- The Compose project is `ruchoir` in production, and in development the directory's name and a
  hash of its path (`render::project_name`), so two development directories never share volumes
  (the second would find the first's database, with other passwords, and Propolis would not start).
  A development instance written before this rule ran as `ruchoir`: its old volumes stay under that
  name (`docker volume ls`), and the instance starts on fresh ones.
- In development the hub's `HUB_PUSH_RELAY_URL` is empty: without it the hub would call the
  publisher's production relay (its default) for every phone a developer subscribes.
- A fresh Garage stores nothing until its layout is applied, the drive's key imported and the
  `drive` bucket created and allowed to the key. `up` and `dev` do it after starting the instance,
  through `docker compose exec -T garage /garage` (the image has no shell), and again on every start:
  the layout is applied only while none is, and "already exists" from the key or the bucket is taken
  as done. The commands follow Garage v2's command line, whose flags changed since v1: check them
  against `src/garage/cli/structs.rs` of the pinned tag when bumping the image.
- Garage's secrets stay out of `garage/garage.toml`: it reads `GARAGE_RPC_SECRET` and
  `GARAGE_ADMIN_TOKEN` from its environment, filled from `.env`.
- `postgres/init.sh` runs once, on an empty data directory: a product added to an instance that
  already ran has no database yet. Create its role and database by hand with the statements of
  `init.sh` (`docker compose exec postgres psql -U ruchoir`) until the installer does it.
- The drive's private keys go to the drive alone: `keys/drive-auth.pem` is mounted in its
  container, and Propolis's registry holds the public halves of both.
- Each service has its own Valkey database index: Propolis `0`, the hub `1`, the drive `2`, the
  calendar `3`, the chat `4`. A new product takes the next one.
- The calendar mails people invited by address. In development it uses Mailpit as Propolis does; in
  production the installer sets no relay for either (the operator's `compose.override.yaml` does),
  and without `CALENDAR_SMTP_HOST` the calendar logs those mails instead of sending them.
- The calendar declares no resource scope of its own (no other service calls its API), so its client
  has no `resource_scopes`. It asks `drive:held.manage` only when the drive is installed: Propolis
  refuses a scope no resource of the instance declares.
- The chat's pages open the hub's socket with a ticket the chat asks for them, with the person's
  token exchanged at Propolis for one for the hub (ADR 0016). Its client is given the grant
  `urn:ietf:params:oauth:grant-type:token-exchange` and a `[[client.token_exchange]]` entry, the
  hub's resource as `audience` with no scope (the hub asks none of a person's token). The drive's
  and the calendar's pages ask no ticket, so their clients have neither. The audience must be the
  hub's resource exactly, and the rewritten check refuses one that is no resource of the registry.
- The chat reads the first link of a message for its preview (`CHAT_UNFURL_ENABLED`, `true`), never
  on its own domain and its subdomains: every host of the instance is covered, so
  `CHAT_UNFURL_DENY_HOSTS` stays unset.
- `dev --source` builds the images of Propolis, the drive, the calendar and the chat with the npm
  token as the BuildKit secret `npm_token` (`--secret id=npm_token,env=NODE_AUTH_TOKEN`), the id
  their Dockerfiles name.
- The office editor has a hostname of its own, `office.<domain>`, which the proxy routes to the
  drive (`service: drive`), never to the engine: the drive tells the editor's requests by their
  `Host` and relays them, WebSocket included, to `http://office`. The drive refuses to start when
  that host is its own. It is not a service of the instance (no database, no client, not in the
  manifest, whose services are the products; the drive announces it at `GET /api/v1/office`), but
  it needs its DNS name, and its certificate: in development `dev_ca::names` covers it through
  `Instance::hosted`.
- The engine is on the `office` network alone (`internal: true`, no route out), which only the drive
  shares besides the instance's network. It calls the drive's WOPI listener at `http://drive:8081`
  (`ALLOW_PRIVATE_IP_ADDRESS`), published nowhere. `JWT_SECRET` stays empty: the drive never calls
  the engine's own API, and the engine draws a random secret.
- The patched pages of `assets/office/patches/` were taken from Euro-Office 9.3.4: never mount them
  over another version. To move `office::IMAGE`, check each defect upstream (the monolith's
  `infra/office/README.md` lists them), drop the patches it fixes, take the others' pages from the
  new image (`docker create`, `docker cp`) and apply the marked changes again, then check a session
  end to end. The drive's stand-in engine serves 9.3.4's discovery too.
- The engine can take minutes to answer on its first start (fonts, themes; `start_period: 600s`), and `up --wait` waits for it.

### Releases of the installer

No release workflow yet: a tag of this repository publishes nothing, and the installer is built
from a checkout (`cargo install --path .`). The images it runs are the services' own.

### Boundaries

- Configures and connects the products; holds none of their logic.
- Propolis takes no part in discovering what is installed (ADR 0004).

### Checking the work

- The conventions check, with a clone of `Ruchoir/.github` at `$RULES`:
  `bash "$RULES/scripts/check-conventions.sh" "$RULES/common-rules.md"`, from the root.
- `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test`, and
  `cargo deny --config "$RULES/deny.toml" check`, as the shared `rust` workflow runs them. The
  migration's test runs only with `RUCHOIR_MIGRATE_TEST_DATABASE` set (README, "Testing it"): set it
  when `src/migrate/` or a fixture changes.
- The end-to-end test (`e2e/`, Playwright, an accepted exception for tests only): with a
  development instance up (`ruchoir-install dev --source ..`), `pnpm install` then `pnpm test` in
  `e2e/`. In CI the job runs once the repository variable `RUCHOIR_E2E` is `on`. It checks out
  Propolis and the hub with `RUCHOIR_E2E_TOKEN`, a fine-grained token that reads their contents only
  (the job's own token, for a repository that is public); the installer's own token reads the
  `@ruchoir` npm packages, which must grant this repository access.
